# W22.8 多 mask 管线验证报告（K=1 vs K=2 dry-run）

- 日期：2026-08-05
- 工作项：W22.8（多 mask 数据管线，commit `890ac8c`）
- 验证目标：spec `2026-08-05-w22-8-multi-mask-pipeline-design.md` §6 gate 4-5
- 范围：CPU dry-run，40 optimizer steps，固定 seed=42

## §1 结论一句话

K=2 端到端跑通，loss 曲线与 K=1 同量级，per-step wall time 1.04× K=1
（spec §6 gate 4 "不发散" + gate 5 "avg_step_s 比值"两项满足）。K>1
相对 K=1 的实际收益需要 Atlas + 真实视频 + 长训练才有统计效力，CPU
dry-run 只能排除「实现发散 / 接线错误」这一类硬错误，做不到。

## §2 关键改动（验证基础设施）

写验证脚本时发现 `scripts/w22_7_run_arm.py::_dry_batch` 只产出
`bool_masked_pos`（K=1 形态），原 W22.7 dry 模式**绕过 dataset**，
直接走 `batch_fn`，所以 cfg 配 `num_masks=2` 也不会触发 W22.8
新接的 K>1 分支（`JEPAObjective.loss_fn` 只在
`bool_masked_pos_k in batch` 时走 K>1）。**初版验证无效**：
K=1 / K=2 的 loss 曲线逐位相同，因为两条都走的 K=1 路径。

修法（本次 commit 的一部分）：

- `scripts/w22_7_run_arm.py` 新增 `--num-masks` flag（默认 1，
  向后兼容 W22.7），透传到 `_dry_cfg(arm, num_masks)`。
- `_dry_batch(i, num_masks=1)`：K=1 行为与 W22.7 逐位相同；K>1 时
  按 `np.random.default_rng(i)` 多抽 K-1 个 mask，组装
  `bool_masked_pos_k: (1, K, N)`，且 `masks[0]` 与 K=1 时的
  `bool_masked_pos` 复用同一抽样（保证跨 K 可比对）。

这一改让 W22.7 dry 模式**第一次**能真正跑 K>1。

## §3 数字（CPU dry-run，B-arm，40 steps，save_every_n=4）

| 指标 | K=1 | K=2 | 备注 |
| --- | --- | --- | --- |
| wall_time_s | 6.37 | 6.63 | 1.04× |
| avg_step_s | 0.159 | 0.166 | **1.04×**（spec §6 gate 5） |
| loss_fn_s（累加） | 0.52 | 0.67 | 1.30×（predictor 跑 2×） |
| context_forward_s | 0.25 | 0.29 | 1.15×（autograd graph 变大的副作用） |
| loss step 1 | 27.66 | 27.71 | 同量级 |
| loss step 40 | 8.74 | 8.66 | 同量级，K=2 略低 |
| recon_cosine step 40 | 0.0158 | 0.0154 | 2.5% delta |
| token_variance step 40 | 0.994794 | 0.994791 | 3e-6 delta |
| effective_rank step 40 | 61.60 | 61.59 | 0.02% delta |
| linear_probe_acc | 1.000 | 1.000 | 探针集过易，不可区分 |
| knn_hit_rate | 1.000 | 1.000 | 同上 |

## §4 解读

1. **K>1 路径已接通**：loss_fn 的 1.30× 累加时间是 K=2 真正跑了两遍
   predictor + 一次 mean 的直接证据；之前的「byte-identical 12%」
   是 K>1 没真跑 + CPU 调度噪声叠加的假象。
2. **Wall 摊销 1.04×**：predictor 只有 35K 参数（35,904），是 22M
   encoder 的 0.16%。K=2 的 loss_fn 增量（0.15s / 40 步 = 3.8ms/步）
   被其余开销（EMA gather、checkpoint 保存、probing 重建）摊薄。
   与 spec §7 风险 #2 预测一致：K>2 时还需要看 Atlas 实测，但 K=2 的
   摊销已经够低。
3. **指标几乎不动**：random init + 40 dry step + 合成探针集（4 类、
   noise 0.1）的组合，模型基本没在学。`token_variance ≈ 0.995`、
   `linear_probe_acc = 1.000` 两条都说明探针区分度为零。
   K>1 的正则收益（spec §1 引用 Bardes 2024）需要真实数据 + 长训练
   才能显现；CPU 40 步在物理上不可能分辨。
4. **「不发散」是这次验证的硬门槛**：K=2 不会比 K=1 跑挂、不会 OOM、
   不会数值爆炸——这些都满足。Loss 末值 8.66 vs 8.74 在随机扰动量级，
   不构成发散。

## §6 复现命令

```bash
# K=1
PYTHONPATH=. python3 scripts/w22_7_run_arm.py --arm b --mode dry \
    --num-masks 1 --steps 40 \
    --out bench_results/w22_8/b_k1 --save-every-n 4

# K=2
PYTHONPATH=. python3 scripts/w22_7_run_arm.py --arm b --mode dry \
    --num-masks 2 --steps 40 \
    --out bench_results/w22_8/b_k2 --save-every-n 4
```

原始数据落盘到 `bench_results/w22_8/{b_k1,b_k2}/{metrics.jsonl,throughput.json}`。

## §7 不在本次验证范围

- K=2 的「正则收益」——需要 Atlas pilot 200+ steps（spec §6 gate 4
  备注）。CPU 干跑无法证明 K>1 真的拉开 token_variance。
- K>2 的显存/吞吐——`vjepa2_vitl_1.2b.yaml` 注释里 v1 推荐 K=2。
  K=4 / K=8 留作后续 Atlas pilot 测量项。
- 端到端真实数据路径——W22.7 A/B/C 已经在做（pilot 200 步，Atlas）。
  K=2 与 K=1 在 A/B/C 框架里的对照实验是 W22.8 pilot 阶段的下一步。
